# 接入形态决策

## 判断树

```
宿主（要接入的那个 Agent / 它的 Harness）
  │
  ├─ 它已经有可寻址的常驻 HTTP 服务吗？
  │    └─ 有 → 普通进程形态：自己 POST /heartbeat 注册，wake=http 指自己
  │
  ├─ 它是插件化架构、能力由插件组合、希望随 Core 启动吗？
  │    └─ 是 → Adapter Plugin 形态
  │
  ├─ 它完全没有可寻址入口（桌面端 / 纯交互式）吗？
  │    └─ 是 → 仍可用 Plugin 形态：
  │            Adapter 听着 ANP_PLUGIN_PORT 上的 /anp/wake，
  │            代管身份的 wake 直接指过去
  │
  └─ 宿主既没有端点、也不能被 Core 拉起？
       └─ 退成 queue 档：Agent 自己周期 POST /messages/receive
```

**不预设答案。** 先看宿主真实能力，再定形态；两者跑的是**同一套协议**。

## 两种形态对照

| | 普通进程 | Adapter Plugin |
|---|---|---|
| 身份来源 | 自己 `/heartbeat` 注册 | Core 拉起 + `/anp/register` 送身份和令牌 |
| 谁拉起进程 | 自己 / 平台 | Core |
| 典型场景 | CLI Agent、已有常驻服务的 Agent | 要挂进生态、随 Core 启动 |
| 参考实现 | `examples/adapter_demo/` | `examples/adapter_plugin/` |
| 差别 | 只在**身份怎么来的、谁拉起进程** | 同一套协议 |

## 两个身份（P0-1）

```
ANP Core
   ├── Adapter Plugin 身份   anp.adapter.<platform>      ← 管理 adapter 自身
   └── Agent 身份            <platform> / <platform>-<n> ← 代表外部 Agent 通信
```

| 规则 | |
|---|---|
| 2a | 两个身份各有各的 token，**任何情况下不互换、不共用、不派生** |
| 2b | plugin token 只用于：`/plugin/register`、取自身配置、收 `/anp/register` |
| 2c | agent token 只用于：代该 agent 发信 / 收信 |
| 2d | 一个 Adapter Plugin 可管理 **N 个** Agent 身份 |
| 2e | **一个 Agent 身份只归一个 Adapter 管**（否则抢 wake 端点，行为不确定） |
| 2f | Agent 身份被顶替的防护由「已有身份必须带对令牌」保证，与 Adapter 无关 |

### 命名约定

```
Adapter Plugin 身份：anp.adapter.<platform>
Agent 身份：        <platform> 或 <platform>-<instance>
```

★**一个身份名一经注册不得更改**——换名等于换人。★

### 令牌信任假设

```
Adapter 持有 agent token  → 「和同一 OS 账户等信任」        可接受
Adapter 持有 hub.secret   → 「只有 Hub 能合法生成签名」失效  ★绝对禁止★
Adapter 持有 admin token  → 不必要，且 /plugin/register 明确不接受
```

## 四档 delivery mode 选择

| 你的平台 | 选它 | 说明 |
|---|---|---|
| 有常驻 HTTP 服务，能被 POST | **`http`** | 首选：最省事、最可靠、真实部署下唯一稳的 |
| 只有 CLI / 无从寻址入口，但要随信即起 | `exec` | 注意信任校验，Plugin 形态下常常走不通 |
| MCP / 纯轮询 / 桌面端 / 不想被打断 | `queue` | **合法终态**，不是"没接好" |

**判定规则**：`kind` 显式 `queue` → queue；`http` 有 `url` → http；`exec` 有 `command` → exec；
**其余一律 queue**（包括压根没有 `wake` 字段的身份）。

### 三态标记必须分清

```
wake=false           → skipped    → 发送方选择不唤醒     wake_skipped = true
wake.kind=queue      → no_push    → 收件人没有 push 目标 wake_skipped = "no_push_target"
http/exec 失败       → failed     → 可以进入 retry       wake_skipped 缺失
```

**禁止合并成一个布尔。**

### `exec` 的边界

- **进程契约**：每封信念一次进程、投环境变量、然后不再管它。
- **不定义** Adapter 内部的宿主生命周期——你可以在被拉起的进程里再起常驻服务，Core 不依赖。
- **真实部署陷阱**：`exec` 引用的脚本要过 Core 信任校验（只认信箱安装目录），
  而 Plugin 装在 `<home>/plugins/<id>/` 永远在外面 → 被拒。
  → **Plugin 形态一律用 `http`**：插件自己听着 `ANP_PLUGIN_PORT`。

## Adapter 最小职责（4 必须 / 6 禁止）

**必须**：① 托管身份　② 实现唤醒　③ 语义翻译　④ 回收回信

**禁止**：
- 做投递决策（重投 / 退避 / 在线判断）
- 读别人的收件箱、读 `keys.json` / `ledger.jsonl`
- 持有或使用 hub signing secret
- 代替 Core 签收
- 用自己的身份冒充 agent
- import Core 的 `src/`

> **硬规则**：Core 是唯一真相源。Adapter 可以持有状态，但必须能在**状态全丢后从 Core 恢复**。
> Adapter 侧的 roster / 会话缓存都只是缓存，丢了重启即可，不能反过来让 Core 依赖它们。

**依据**：Adapter Spec §1、§2、§4、§12.1；Plugin Spec §3。
