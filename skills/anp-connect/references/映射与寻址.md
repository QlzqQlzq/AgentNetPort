# 映射与寻址

## 一、对象映射表（写代码前先填）

| ANP 侧 | 你的平台侧 | 备注 |
|---|---|---|
| Agent identity | ? | ANP 只认身份名；**注册后不得改名** |
| `Envelope.from` / `to` | ? | **是人**，不是会话 |
| `Envelope.reply_to` | ? | 回信必须带回 |
| `Envelope.correlation_id` | ? | 对话线；回信原样带回 |
| `meta.context_id` | ? | 一封信里对话线 id |
| `meta.from_workspace` / `to_workspace` | ? | **坐标**：期望在哪儿干活 |
| `meta.session_policy` | ? | `new` / `reuse` / `auto`（默认） |
| `meta.session` | ? | 点名要落在哪个会话 |
| `meta.need_reply` | ? | `true` 才要求答复 |
| delivery mode | ? | Core 只认 http/exec/queue |
| 公开名册字段 | 平台别名 / 短名 / 标题 | **不放进 Core**，Adapter 自己持有 |

## 二、★Workspace / Session 映射★

### 错与对

```
✗ 每个 Workspace 注册成一个 ANP Agent
✓ ANP Agent  →  Adapter  →  平台 Workspace / Session
```

### 正确形状

```
ANP Agent                         ← 一个身份（或 N 个，由 Adapter 代管）
    ↓
Adapter                           ← 唯一知道"信该投到哪扇门"的东西
    ↓
平台 Workspace / Session          ← 平台原生对象，Core 看不见
                                   原生 ID 可以是随机值
```

### 四条规则

1. **Agent ↔ Workspace/Session 的映射由 Adapter 自己维护**；Core 不需要理解平台原生 ID。
2. 平台已有 Workspace 生命周期 / 标题 / 最近使用时，**跟随平台已有机制**，
   不要在 ANP 里重造一套 Workspace 系统。
3. 用**工作区标题**做用户侧解析（用户会说「<某个工作区标题> 那个工作区」）时：

   ```
   标题 → 候选 Workspace → native workspace ID   ← 全部在 Adapter 里
   ```

   Core 不保存平台工作区标题，也不参与这段解析。
4. **发信时坐标要自动带**：`from_workspace` 缺省时从「启动上下文的 `cwd` → 本进程 `cwd`」补上；
   调用方显式写的值不被覆盖。

### ★不要混为一谈的两个概念★

```
ANP conversation / correlation        ← 对话线（钥匙），跨平台存在
平台原生 Workspace / Session ID       ← 平台坐标（可能是随机值）
```

**它们属于不同层。** 前者随信封走、回信带回；后者只在 Adapter 内部使用。

## 三、收信侧的会话决策（收信通道只执行）

**分工**：Agent 与收信通道只负责「发信 / 收信」；**"怎么发、发给谁、要不要开新对话"由 Core 决定**。

```
寄件人            信箱（Core）                       收信通道（你）
  │  发信 + 诉求    │                                    │
  ├───────────────► │ ① 查会话大脑（名册 + 对话线绑定）    │
  │                 │ ② 在信封里盖 meta.session 章        │
  │                 ├───────────────────────────────────►│ ③ 照章执行：
  │                 │                                    │    mode=reuse → 注入该会话
  │                 │                                    │    mode=new   → 新建会话
  │                 │ ⑤ 记住落点 ◄───────────────────────┤ ④ 回报：新会话 id
  │                 │   （context_id → session_id）        │    与自己在用的会话名册
```

### 决策顺序（理解即可，不用自己实现）

```
① 寄件人点名 session        → 在名册里就复用，否则开新对话（不猜）
② session_policy = new      → 直接开新对话
③ context_id 已绑定会话      → 复用绑定（回信的默认路径）
④ 按 to_workspace 找：精确 → 子目录 → 上级工作区；
   同级先看 running，再看"用户最近发言时间" → updatedAt
⑤ 什么都没有时：恰好 1 个会话在跑 → 认作"同一件事的后续"，继续用它；
   有多个在跑、或没有在跑 → 不猜，开新对话
⑥ 兜底：名册只有一个会话就用它；否则开新对话
```

> **⑤ 的由来**：若把"缺信息"一律当成"新话题"，同一个人的连续来信会被拆成一堆新对话。
> 所以缺路由信息时**默认延续当前对话**，而不是新开。

### 你要做的两件事

- 用 `POST /session/roster` 上报**名册**（`adapter` / `workspace` / `sessions[]`）——
  只有你知道本地有哪些会话、哪个是用户最近在用的。
  名册超过 TTL（默认 300 秒）没更新即视为过期，过期时 Core 当作"看不到会话"，只会开新对话。
- 执行完新开对话后用 `POST /session/bind` **回报落点**，Core 记住这条对话线。

## 四、寻址（可选能力）

### 归属

| 谁 | 负责 | 不负责 |
|---|---|---|
| **Core** | 公开名册 `GET /agents`、canonical ID、投递 | 不解释「负责 <某个项目> 的那个」「昨天那个工作区」「这个项目」；不懂 Workspace / Session / 平台标题 |
| **Adapter** | 收模糊目标、搜候选、结合平台信息、排序、折成 canonical ID、必要时回候选让人再指一次 | 不做投递决策 |

> Core 负责"把信送给谁"；Adapter 负责"用户说的那个谁到底是谁，以及平台里具体该投到哪扇门"。

**不需要新增 Core API。**

### 四个出口

```
RESOLVED               唯一目标 → target = canonical Agent ID
AMBIGUOUS              多个相近候选 → 返回 candidates，★不猜★
NOT_FOUND              名册里没有匹配（可附最接近的，仅作提示）
INVALID_TARGET         目标本身不合法
DIRECTORY_UNAVAILABLE  名册取不到
```

保留态（传输层用）：`NETWORK_ERROR` / `CONNECTION_FAILED` / `ANP_OFFLINE` / `ANP_MAINTENANCE`。

### 规则

1. **精确优先**：归一后与某个 Agent ID 相同 → 直接 RESOLVED。
2. **匹配只用公开信息 + 本地提示**：name / alias / skills / caps / description / 平台短名 /
   平台工作区标题 / tags；普通字符串比较（归一化 + 词元命中 + 区分力加权），**不引入任何模型**。
3. **`last_used` 只能排序，不能覆盖歧义**：只有当候选本来就不相上下、并列者都有**同一来源**的
   `last_used`、且领先者确实新得多（年龄差 ≥ 门槛且至少新若干倍）时，才允许据此收窄；
   达不到门槛 → **AMBIGUOUS**。缺 `last_used` 或时间戳异常（未来时间）→ 不作证据。
4. 没有任何匹配 → NOT_FOUND。
5. **AMBIGUOUS 不得自动挑选。**

### ★`last_seen` ≠ `last_used`★

| 信号 | 名字 | 从哪来 | 语义 | 能做什么 |
|---|---|---|---|---|
| `last_seen` | 名册字段 `GET /agents` | Core：账本里该身份**最后一条记录**的时间戳（心跳/续约/探活） | 最近**活跃**（它还活着） | **只用于排序**；★默认不许替用户挑人★ |
| `last_used` | **Adapter 自己记** | 平台侧"最近一次真的被处理过" | 最近**被用过** | 排序 + 真并列时破并列 |

`/agents` **给不出** `last_used`（Core 的 `delivered_at` / `read_ts` / `read_by` 不在名册里）。
想要这条更强的信号，就**自己记**：

```python
local.add(agent_id, last_used=time.time())   # 平台记录 → source=platform
```

**四条硬规则**：

1. `last_seen` 只来自名册、`last_used` 只来自 Adapter 提示，**互不代填**。
2. 候选视图**同时给** `last_used` / `last_used_source` / `last_seen`，调用方看得见来源。
3. 破并列只在**并列的每个候选都有同一来源**的最近信号时进行：
   - 只有一部分候选有记录 → **不许用**（否则选出来的是"唯一有记录的那个"，不是"最近的"）；
   - 只有 `last_seen` → **默认不许用**。
4. `decided_by` 与 `reason` 必须写明信号来源（`recency.platform` / `recency.heartbeat`），
   且**心跳来源的措辞只能说"最近活跃"，不许说"最近用过"**。

### Resolve 与 Send 必须分开

```
Resolve("负责 <某个项目> 的那个")  → AMBIGUOUS / candidates   ← "不知道发给谁"
Resolve("<canonical-agent-id>")   → RESOLVED / agent_id       ← 知道发给谁了
Send(agent_id)                    → ok=true, wake={...}       ← "投不投得出去"是另一件事
```

> **两种失败绝不允许混成一种错误。**

### 关于 AI 寻址

**不要强制使用 AI 做寻址。** 基础行为只需支持：精确 → RESOLVED；模糊唯一 → RESOLVED；
多候选 → AMBIGUOUS + candidates；无候选 → NOT_FOUND。
如果以后认为需要 Resolver Agent / LLM，**作为可选扩展**加。

## 五、`ok=true` 的语义（最容易误读）

```
POST /messages/send → ok = true
```

**只表示「消息已经成功持久化」**，不表示对端已收到，更不表示已消费。

真正的投递状态看两处：

```
wake 字段             → 这一次投递的结果（kind / ok / error）
消息记录里的状态字段   → delivered_at / attempts / next_retry_at /
                         last_error / read / wake_skipped
```

**依据**：Adapter Spec §8.5、§8.6、§8.7、§9；Protocol §2、§2.2。
